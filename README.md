# Мониторинг занятости BTL

## Быстрая установка на сервер

Скачайте [ZIP проекта](https://github.com/shukhratbekovb/test/archive/refs/heads/main.zip), распакуйте в отдельную папку и запустите **install.cmd от имени администратора** на Windows Server. Установщик настроит Python, IIS, HTTPS, базу, автозапуск и резервные копии.

Адрес по умолчанию: **https://monitoring.btl.local**. Начальные реквизиты: `C:\Apps\BTL\secrets\initial-admin.txt`. Для сотрудников нужны DNS-запись на сервер и доверенный HTTPS-сертификат.

Подробности, параметры и обновление: [deploy/WINDOWS.md](deploy/WINDOWS.md).

Серверное веб-приложение для общего учёта работ института. Все пользователи одной установки работают с одной SQLite-базой на сервере. Интерфейс использует корпоративную сине-голубую палитру, отдельную страницу входа и адаптивную верстку. Это самостоятельная авторизация; подключения к СЭД пока нет.

## Возможности и права

- **Сотрудник:** видит только свои записи, регистрирует работы за себя и может удалять только созданные им записи.
- **Руководитель отдела:** видит данные только своего подразделения, регистрирует работы сотрудников своего отдела и ведёт его справочник.
- **Администратор:** видит данные института; в панели управления добавляет подразделения и должности, создаёт карточки сотрудников с отдельными полями Ф.И.О. и назначает сотрудникам учётные записи.
- Пароли хранятся как salted PBKDF2-HMAC-SHA256 hashes; предусмотрены CSRF-проверка, ограничение попыток входа, HTTP security headers и завершение остальных сессий при смене пароля.
- Пароль учётной записи должен содержать не менее 10 символов, включая минимум две заглавные и две строчные латинские буквы. На дашборде показывается численность сотрудников в каждом подразделении.
- В дашборде выбор подразделения показывает список его сотрудников и их статус в штате. Удаление карточки сотрудника отключает привязанную учётную запись и сохраняет историю работ; подразделение нельзя удалить, пока в нём есть карточки сотрудников, а должность — пока она назначена сотрудникам.
- Рабочие записи сохраняют снимок Ф.И.О., отдела и должности; отключение сотрудника не удаляет журнал работ.

Ограничение доступа проверяется на сервере, а не только скрытием элементов интерфейса. Администраторский аккаунт создаётся при первом запуске из локального `.env`; создавать администраторов через публичную форму нельзя.

## Ручная установка на сервер Windows (альтернатива)

Используйте отдельный сервер или постоянно включённый компьютер с Python 3.12+, доступный сотрудникам в сети института. Одновременно запущенный экземпляр приложения должен быть один: SQLite-файл нельзя размещать на сетевой папке или совместно открывать из нескольких экземпляров приложения.

1. Установите Python 3.12 или новее.
2. В PowerShell из папки приложения скопируйте шаблон и задайте уникальные значения `SECRET_KEY` и `ADMIN_PASSWORD` (пароль администратора — не менее 12 символов):

   ```powershell
   Copy-Item .env.example .env
   python -c "import secrets; print(secrets.token_urlsafe(48))"
   ```

   Скопируйте выведенный случайный ключ в `SECRET_KEY` в файле `.env`; задайте новый пароль `ADMIN_PASSWORD`. `.env` содержит секреты: ограничьте права доступа к нему администраторами сервера и системной учётной записью службы резервного копирования.

3. Установите зависимости:

   ```powershell
   python -m venv .venv
   .\.venv\Scripts\python.exe -m pip install -r requirements.txt
   ```

4. Подготовьте папки для базы и резервных копий и запустите:

   ```powershell
   New-Item -ItemType Directory -Force data, backups
   .\start_server.ps1
   ```

5. Настройте HTTPS на корпоративном reverse proxy (например, IIS с URL Rewrite/ARR), перенаправьте запросы на адрес приложения и включите `COOKIE_SECURE=1` в `.env`. Не публикуйте порт приложения напрямую в Интернет. Внутри доверенной сети используйте корпоративный TLS-сертификат и сетевые правила доступа. После изменения `.env` перезапустите приложение.
6. Проверьте вход администратором, добавьте отделы и сотрудников, затем создайте им учётные записи и назначьте руководителей. Временные пароли передавайте по защищённому каналу; пользователь может сменить пароль после входа.

Приложение слушает адрес и порт из `.env` (шаблон настроен на `127.0.0.1:8080` за HTTPS-прокси). Не храните `.env`, базу и резервные копии в публично доступной папке или в системе контроля версий. На сервере ограничьте входящий доступ к приложению сетевым экраном; внешний доступ должен идти только через HTTPS-прокси.

## Резервное копирование и восстановление

Создать согласованную копию SQLite с проверкой целостности и хранением последних 30 дней:

```powershell
.\backup.ps1
```

Для ежедневного запуска в 02:00 откройте PowerShell **от имени администратора** и выполните:

```powershell
.\register-backup-task.ps1
```

Задача запускается от `SYSTEM`; проверьте, что этот аккаунт может читать `.env` и файл базы, а также записывать в `backups`. После регистрации выполните `.\backup.ps1` вручную и проверьте наличие файла `workload-*.sqlite3` в `backups`. Резервные копии содержат персональные данные и должны храниться с ограниченным доступом; копируйте их также на защищённое отдельное хранилище согласно правилам института.

Для восстановления остановите приложение, выберите проверенную копию, сохраните текущую базу отдельно и восстановите копию на путь из `DATABASE_PATH`. Затем запустите приложение и убедитесь, что данные доступны. Перед вводом в эксплуатацию проверьте восстановление на отдельной тестовой копии, а не на рабочей базе.

## Данные и доступ

- База по умолчанию: `data\workload.sqlite3`; каталог задаётся `DATABASE_PATH`.
- Копии по умолчанию: `backups`; каталог задаётся `BACKUP_DIR`, срок хранения — `BACKUP_RETENTION_DAYS`.
- При первой инициализации создаётся один активный администратор из `ADMIN_USERNAME` и `ADMIN_PASSWORD`. Значения пароля не записываются в открытом виде в базу.
- Регистрация новых пользователей открыта только администратору. Самостоятельного создания аккаунтов и интеграции с учётной записью СЭД нет.
